# Galactica

Galactica analyzes a JavaScript or TypeScript repository into one internal model. The agent commands and the HTML page both render that model, so they never disagree.

## Terms

- **Package:** a workspace package in a monorepo. A single-package repository has one package.
- **Module:** one source file, including `.vue`, `.svelte` and `.astro` files.
- **Area:** a group of modules within one package, usually a folder. The HTML page draws each area as a box. Galactica groups areas automatically, and `galactica.config.json` can override the grouping.
- **Symbol:** an exported function, class, component, type, interface, enum or constant.
- **Edge:** an import from one module to another, resolved through tsconfig paths, workspace packages and barrel re-exports to the module that defines the symbol.
- **Layer:** an area's position in the dependency order within its package. An area only depends on areas in lower layers. Areas in an import cycle share one layer. Tests and stories never affect layers, and an area of only tests and stories sits one above the highest area it imports.

## Structure

- `src/bin.ts`: the `galactica` executable. It checks the Node.js version through `src/node-version.ts` before anything else loads, then runs `main` from `src/cli.ts`. `src/node-version.ts` holds the minimum, which `package.json` `engines` repeats and `tests/node-version.test.ts` keeps equal.
- `src/cli.ts`: the command line. It parses argv against the command table, loads `galactica.config.json` once through `src/config.ts`, analyzes the repository through `src/model-cache.ts`, with no cache when `--no-cache` is given, runs the command and prints its JSON object or its text. A `ConfigError` from any step fails the command with its one line. For `html`, it writes the page from `src/html.ts` to a file and can open it, taking the link template from `--source-url`, else the config's `sourceUrl`. For `init`, it installs the skill through `src/skill.ts`. It holds no command logic.
- `src/commands.ts`: the command table. Each entry gives a command's argument, the options it takes, and the pure function from the `Repository`, the `Graph` and the analysis warnings, to its `--json` object. Adding a command is one entry here and one renderer in `src/render.ts`.
- `src/render.ts`: the text form of each command, built only from its `--json` object, so text and JSON never disagree.
- `src/subjects.ts`: what a command argument names. `resolveSubject` reads a module path, package name, package directory or area path, from the current directory and from the root, and `resolveModule` reads a module path only.
- `src/queries.ts`: the answers of `where`, `outline`, `uses` and `deps`, built from the `Graph`. `uses` and `deps` share one breadth-first walk, and `usesOf` and `depsOf` answer for a subject already resolved.
- `src/overview.ts`: the answer of `overview`, with each area's modules ranked by their importers.
- `src/html.ts`: the HTML page. `htmlOf` fills `src/page/page.html` with the stylesheet, the page script and the page data, inlined so the page makes no network requests.
- `src/page-data.ts`: what the page draws. `pageData` turns the `Graph` into the compact object the page embeds, with areas and modules referred to by index, and each relation list stored as the gaps between ascending indexes, which `src/page/indexes.js` reads back. Each module and area carries what `uses` and `deps` answer for it at depth 1, so the page never walks the imports itself. Its shape is private to the page.
- `src/source-links.ts`: how the page links to source. `githubTemplate` reads a git remote URL into a link template, `templateProblem` rejects a template that cannot work, `linkBase` picks the ref to take the merge base with, and `pageSource` fills `{commit}` into the template for the page data. Pure. `src/page/links.js` builds each href from it on the page.
- `src/git-source.ts`: `pageSourceOf` reads the remote, the newest commit the remote has (HEAD, else a merge base, from local refs only) and how many commits HEAD has beyond it, the root's directory within the repository and whether tracked files changed, with each filter driver of the repository's own config turned off, and gives the page's `source`, or undefined when git cannot link.
- `src/row-order.ts`: the order of the boxes within each row of the page. `orderRows` reduces crossings between rows with a barycenter sweep, in path order where nothing pulls.
- `src/page/`: the page template, `page.css`, `page.js`, `search.js`, `links.js` and `indexes.js`, plain files that the build copies to `dist/page`. The scripts are type-checked against `src/page-data.ts` through JSDoc, and build the page with no framework. `search.js` lists what the search field finds and ranks the matches, with no DOM, so `tests/search.test.ts` imports it. `tests/page.test.ts` drives the built page in headless Chrome through `tests/browser.ts`, and skips when it finds no Chrome.
- `src/skill.ts`: the agent skill `init` installs. `skillFile` puts the command into the template and records the Galactica version and a hash of the written file in its frontmatter `metadata`. `ruleFile` writes the Cursor rule that points to it. `agentFiles` lists what `init` writes, and `installSkill` writes it to `.agents/skills/galactica/`, `.claude/skills/galactica/` and `.cursor/rules/galactica.mdc`, and keeps a file whose hash no longer matches, since someone edited it.
- `skills/galactica/SKILL.md`: the skill template, in the layout the skills CLI discovers, and shipped in the package. It names `npx @cognitap/galactica`, which `init --command` replaces. `tests/skill.test.ts` checks its frontmatter against the Agent Skills specification.
- `src/contract.ts`: the public `--json` output types and `SCHEMA_VERSION`. It imports nothing, which `tests/contract.test.ts` enforces.
- `src/config.ts`: `loadConfig` reads `galactica.config.json` at the root into the readonly `Config` of `src/model.ts`, the empty config when there is none, and throws a `ConfigError` naming the key for anything it cannot use. Discovery, the areas, `kindOf` and `html` take that `Config` and never read the file. A problem that needs the modules, two kinds matching one module or an area outside its module's package, is a `ConfigError` from `kindOf` or `areasOf`.
- `schema/galactica.config.schema.json`: the JSON Schema of the config, shipped in the package. `tests/config.test.ts` checks it with `tests/json-schema.ts` against `loadConfig` on every config in `tests/config-examples.ts` and the README, so the two cannot drift. Add each config a test uses to `tests/config-examples.ts`.
- `src/model.ts`: the `Model` of per-module facts, the `Config`, and the in-memory `Graph` derived from both.
- `src/discovery.ts`: `discover` lists a repository's packages, its modules with their language, kind, tsconfig and package, narrowed by the config's `include` and `exclude`, and the builds its configs declare, and collects config warnings. `compilerOptionsOf` gives the options for one module.
- `src/source-file.ts`: what a path is. `languageOf` classifies a file from its path alone, `kindOf` from its path and the config's `kinds`, and `isScriptLanguage` says whether TypeScript parses the language itself. Discovery and the graph both call `kindOf`, so they never disagree on a kind.
- `src/analysis.ts`: `analyzeRepository` turns a repository root and its `Config` into its `Model`, reading the repository through an `Inputs` of `src/inputs.ts`, the machine as it is by default. It loads TypeScript, so the CLI imports it only through `src/model-cache.ts`. No cache entry depends on the config, so a change to it parses only the modules it brings back. It takes each module's extraction from the cache when the module's size and mtime, or else its hash, are unchanged, and parses it otherwise. Then it resolves every import and follows imports through barrels, on every run. It returns a summary of warnings, unresolved edges, skipped imports and how many modules were reused, reread and parsed beside it.
- `src/extraction.ts`: what one module gives from its own bytes. `extract` parses a module once and reads its symbols and its imports before resolution, so the result holds while the module's hash is unchanged. A framework file gets its implicit component, and the symbols and imports of each script block, shifted to the block's lines.
- `src/frameworks.ts`: the framework table, one entry each for Vue, Svelte and Astro. `scriptBlocksOf` gives a framework file's script blocks with the lines before each, and whether each can export, through `vue/compiler-sfc` or `svelte/compiler`, and through the frontmatter text for Astro. `compilerOf` loads each compiler from Galactica's own optional dependencies, never from the repository being mapped, and `unreadWarnings` gives one warning per language whose files it could not read. Adding a framework is one entry here.
- `src/cache.ts`: the cache of extractions between runs, in `node_modules/.cache/galactica/` or the user cache folder. `readCache` parses the file at the boundary, and anything unexpected, or a cache from another format, Galactica build, TypeScript version or compiler version, reads as empty. A compiler's version is `missing` when Galactica was installed without it. `writeCache` replaces the file by rename through `replaceFile`, which the model cache shares, and never fails a run. The stamp reads the versions of TypeScript and the compilers from their package.json files, so a warm run knows it without loading them.
- `src/model-cache.ts`: the cache of the derived model, in `model.json` beside the extraction cache, and `analyze`, the one way a command analyzes a repository. The file holds one line with the stamp and the fingerprint of everything the model was derived from, then the model and its summary. When the stamp matches and `src/inputs.ts` finds every recorded input unchanged, `analyze` answers from the file without discovery, resolution or TypeScript. Otherwise it imports `src/analysis.ts`, runs it with a recorder, and writes the file, unless a timestamp was too fresh to trust.
- `src/inputs.ts`: what an analysis reads beyond its modules' bytes, as the `Inputs` it reads through, and whether any of it changed. `recordInputs` wraps TypeScript's `sys` and records, before each read, the stat of every file read or stat-ed, the mtime of every directory under the root whose entries decided a probe (existing or not), the stat of every path probed outside the root, a hash of git's listing and a hash of the config. `unchanged` checks a record with stats and one `git ls-files` alone. `fingerprintOf` parses a record at the boundary.
- `src/syntax.ts`: how TypeScript parses a script module. `parseScript` gives the one syntax tree that symbols and imports are read from.
- `src/symbols.ts`: what a module exports. `symbolsOf` reads a module's `SymbolFacts` from its syntax tree alone, with no program and no type checker.
- `src/imports.ts`: what a module imports. `importsOf` reads each import-like statement and `require()` or `import()` call with a literal specifier, and each `export { x }` or `export default x` of an imported name as a re-export from where it came, with its names and syntax, from the syntax tree, as plain data. `resolutionModeOf` gives the mode TypeScript resolves an import in from its syntax and the module's format, without the module's tree.
- `src/import-resolution.ts`: where an import specifier leads. Workspace packages first, unless a `paths` alias matches the specifier, since the alias wins for TypeScript too, then TypeScript's module resolution with the module's options and mode, retried without a `?` query such as Vite's `?worker`, mapped to a module, an external package, an unresolved specifier, or a repository file that is no module and gets no edge.
- `src/barrels.ts`: which module defines each name an import takes. `resolveBarrels` follows imports along named, renamed and `export *` re-exports, from the symbols and edges in the model, and points each at the defining module with the barrels in `via`.
- `src/graph.ts`: the `Graph` a `Model` gives. `graphOf` places each module in its package and area, with its kind and language, from the `Model` and the `Config`, and adds the layers, cycles, reverse edges and symbol index. It is pure and reads no files.
- `src/areas.ts`: which area a module is in. `areasOf` puts a module that the config's `areas` match in the area the first matching glob names. It makes each folder of the other modules an area, and merges a folder of a single module into its parent while the parent holds modules of its own, never above the package's directory.
- `src/layers.ts`: dependency order above the module. `layerAreas` layers the areas of each package from the imports between source and config modules, re-exports aside, and reports the area cycles with the edges that close them. `orderPackages` orders packages by the edges between them.
- `src/cycles.ts`: `moduleCycles` finds import cycles among source and config modules, leaving out type-only imports and re-exports.
- `src/strongly-connected.ts`: the one strongly connected components routine, and the layers over its components, that areas, packages and module cycles share.
- `src/repository-files.ts`: which files a repository has. Uses `git ls-files` so `.gitignore` applies, and a directory walk outside a git work tree, which ignores `.gitignore`. `gitListing` gives git's raw listing, which the fingerprint hashes. Every git command goes through `git`, which turns off `core.fsmonitor` and optional index writes, so the repository's config and hooks run no program.
- `src/workspace.ts`: which packages a workspace names, from `pnpm-workspace.yaml` or the root `package.json` `workspaces`. `packageOf` gives the package of a path.
- `src/package-resolution.ts`: which source module a bare specifier reaches when it names a workspace package, through `exports` or the entry fields, and back from build output to source.
- `src/compiler-settings.ts`: which tsconfig applies to a file, following `extends` and project references, and the defaults when none does. Each config is parsed once per run, its include globs are matched against the repository's file list through TypeScript's own matcher, and its option warnings come from a program with no root files whose current directory is the root, so their text is the same wherever the command runs.
- `docs/json-output.md`: reference for the `--json` output. Update it with `src/contract.ts`.
- `tests/`: `node:test` suites. CLI tests run the built `dist/`, and unit tests import `src/` directly. `tests/temp-repository.ts` writes a throwaway repository for a test, and `tests/models.ts` builds a `Model` in memory for the command tests.
- `tests/determinism.ts`: maps one repository under conditions that must not change the output, through `tests/determinism-outputs.ts`, which runs every command in text and `--json`, and `html`, in one process, and reports each output that differs. `tests/determinism.test.ts` maps representative fixtures from the root with a cold cache, warm from the deepest folder, and with no cache from a copy at another path, each in another locale and time zone, and analyzes every fixture with each directory listing reversed. `node scripts/determinism.ts <repository>...` does the same to clones of real repositories.
- `scripts/pack-and-test.ts`: packs Galactica, installs the archive into a throwaway repository with pnpm, from its store where it can, and runs `--version`, `uses`, `init` and `html` there through the installed `galactica` executable. `pnpm test` runs it after the suites, so CI does, and `pnpm release:prepare` runs it on the release archive.
- `tests/fixtures/<case>/`: one small repository per hard analysis case in `repo/`, with its expected `Model` in `expected.json` and, where the case is about derived data, `expected-graph.json`. `tests/fixtures/README.md` states the conventions. Formatters never touch these files, because the expected files pin line numbers.
- `tests/fixtures.ts`: lists the cases, reads and writes the expected files, and holds the aspect table. Each aspect is one part of the expected files with the issue that implements it. `tests/fixtures.test.ts` checks each expected file against its repository, and compares each implemented aspect with the analyzer's output. `tests/update-fixtures.ts` rewrites the implemented aspects.

## Conventions

- The public contract is the output of the commands, in text and in `--json`. Treat changes to it as breaking. The model and the cache format are private.
- Analyze source with the TypeScript compiler API, and read Vue and Svelte files with `vue/compiler-sfc` and `svelte/compiler`, which Galactica ships as exact-pinned optional dependencies. Astro frontmatter is read as text. Never run the code being mapped: load no module from the target repository, and run git only through `git` in `src/repository-files.ts`. Agents run Galactica on repositories they just cloned or downloaded.
- Write nothing into the target repository except what `galactica init` installs. The cache lives in `node_modules/.cache/galactica`, or in the user cache folder when the repository has no `node_modules`.
- Work with zero config. Every option in `galactica.config.json` is an override, never a requirement.
- The HTML page is one file with no network requests. Inline all scripts, styles and data.
- Output is deterministic: the same repository produces byte-identical output.
- A first run on about 3,000 files takes under 10 seconds, and a command with a warm cache takes under half a second. Do not merge changes that break these targets.
- Support Node.js 24.1.0 and newer. 24.0 prints an ExperimentalWarning on `path.matchesGlob`. Keep `src/bin.ts` and `src/node-version.ts` free of other imports and of syntax older Node.js cannot parse, so an older version gets the check's message.

## Commands

`pnpm check` runs format, lint, typecheck and tests. Run it before every commit.

`pnpm fixtures:update` rewrites the implemented aspects of every expected file from the analyzer's output. Run it when a change to the output is intended, and review the diff under `tests/fixtures` as part of the change. When an issue implements an aspect, give the aspect a check in `tests/fixtures.ts` and remove the cases it finishes from `pendingIn`.

## Releases

Follow [RELEASE_POLICY.md](RELEASE_POLICY.md):

1. Open PR `Release Galactica <version>`: run `pnpm version patch --no-git-tag-version` (`minor` for a breaking change during `0.x`), move Unreleased notes under `## <version>`, commit, and run `pnpm release:prepare`.
2. Squash-merge after CI passes, then run the **Release Galactica** workflow on `main` with `publish`.
3. Verify `pnpm view @cognitap/galactica@<version> dist.integrity` matches `release.json` (never rerun `publish` for an existing version).
4. Create GitHub release `v<version>` titled `Galactica <version>` at `sourceCommit`.
